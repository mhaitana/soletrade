# Soletrade: review and improvement roadmap

**Reviewed:** 17 November 2026. **Wave 1 implemented:** 18 November 2026. **Wave 2 mostly
implemented:** 18 November 2026 (see "Wave 2: what changed" for what is left). **Wave 3
implemented:** 18 November 2026. **Waves 4 and 5 mostly implemented:** 19 November 2026
(see "Waves 4 and 5: what changed" for what is left).

**Scope:** web app and backend (`apps/web`), native app (`apps/mobile`), shared contracts,
database migrations, CI. Four areas: performance, the hAI assistant, UI/UX, and platform
quality. This supersedes `docs/REVIEW.md` (July 2026), whose paths and several findings
predate the monorepo move.

**Method:** three read-only explorations (performance, hAI, UI/UX), a design pass for the
hAI changes, then every finding below was re-read in the source before it was written
down. Items marked "inferred" were reasoned from the code, not observed running. Paths are
relative to `apps/web/src` unless they start with `apps/`, `supabase/` or `docs/`.

**How to read this:** the Findings section records the state before Wave 1. The "what
changed" sections for Waves 1 to 5 list which findings are now fixed and which were
deferred. Waves 6 to 8, the Wave 2 items that need a decision first, and what is listed as
left from Waves 4 and 5 are the remaining roadmap.

## Wave 1: what changed

Wave 1 was "quick wins everywhere": small, independently shippable fixes in six batches.
Everything below is in the working tree; see "Before deploying" for the steps that are not
code.

### Found and fixed during local verification

- **Events published by pages were being dropped.** `instrumentation.ts` registers the
  activity persister and every notification subscriber at start-up, but the server bundles
  that file separately from routes and Server Actions, and each bundle loaded its own copy
  of the event-bus module. Subscribers were registered on one copy; `publishEvent` ran on
  another that had none. Observed on both `next dev` and a production build
  (`next build` + `next start`): creating, sending, paying or voiding an invoice wrote no
  activity entry, no in-app notification and would have sent no email. Earlier test
  records in the local database (October) show the same gap, so this predates Wave 1.
  The registry now lives on `globalThis` (`server/infrastructure/events/index.ts`), with a
  regression test that publishes through a second copy of the module. After the fix the
  production build wrote the activity entries and five member notifications for a test
  invoice. **Check production:** if invoice, quote or invitation emails have not been
  arriving, this is why.

### Done

**Broken flows**

- Invitation emails now link to `/invite/{token}`, the route that exists. Links in emails
  already sent (`/invite?token=`) are redirected by a new `app/invite/page.tsx`, and
  `/invite` is public in the proxy. The invite page returns to itself after sign-in, has a
  working "Sign out and continue as …" action for the wrong-account case, and uses theme
  tokens (it was unreadable in dark mode).
- GST/BAS page, tax lodging and the P&L PDF take their totals from Postgres
  (`get_gst_monthly`, existing `get_book_summary`); the credit balance uses
  `get_credit_balance`. All three were silently wrong past 1,000 rows.
- Invoice, quote and transaction detail dialogs close on success, show errors inside the
  dialog, cannot be dismissed mid-request, and confirm with a toast. The quote "Send"
  dialog no longer stays open after sending.
- GST / BAS and Receipts are linked from the Books header. The command palette lists
  sub-pages (Receipts, GST / BAS, Vehicles, settings sections) and "New …" actions, from
  the same list as the header "New" menu.

**Faster responses**

- Notification handlers (email, PDF attachment, in-app fan-out) run after the response via
  an opt-in `{ deferred: true }` subscription on the event bus. "Send invoice", a
  customer's quote acceptance and the Stripe webhook no longer wait for them. The activity
  feed insert is still awaited.
- Public invoice and quote pages record the first view after the response.
- Parallel reads: invoice detail, invoice PDF, modules settings, mobile dashboard and
  mobile search. Mobile bootstrap verifies the token once instead of twice.
- New indexes for the overdue/expiry/credit crons, the conversation list and the mobile
  job-health counts.
- `loading.tsx` for billing, notifications, audit and assistant.

**hAI**

- One system-prompt builder for web and mobile (`server/application/assistant/prompt.ts`):
  today's date per request in the workspace timezone, workspace name, currency and
  financial-year start, a rule that text in tool results is data, and accurate wording for
  read-only versus actions-on conversations.
- Conversation history: newest messages are kept (it used to drop the newest past 1,000),
  the last 60 are sent to the model, the conversation is read once per turn, and the text
  of every step is saved rather than only the last.
- Tool results: the overview uses the dashboard's SQL summaries; list tools return
  `{ items, returned, hasMore }` with links (default 20, maximum 100); write tools return
  the record number and a link.
- Every write the assistant makes is recorded in the audit log as `assistant.action` with
  `source: "ai_assistant"`, by one wrapper that also covers tools added later.
- Every tool call is shown in the chat as a card: lookups with counts and a "partial list"
  note, changes with a link to the record, failures stated plainly.
- Deleting a conversation and switching write tools on both ask first; the footer says
  what the assistant can do in the current mode.
- Per-call usage log line (model, tokens, cache reads), an output-token cap, a 300-second
  route limit, and an interim cap of 400 model turns per workspace per day.
- Receipts: current SDK structured-output call, credit returned when the model fails,
  the `extractReceipt` tool returns what it read, and the web Receipts page can finally
  start a scan ("Scan a receipt").
- Per-task model settings (`chat`, `light`, `vision`), each defaulting to the chat model.

**UI/UX**

- Success toasts across create, update and delete; creating an invoice or quote opens the
  new record.
- One status map per document type (`lib/domain/{invoices,quotes}/status-display.ts`),
  following the design system's status colours, used by list, detail and public pages.
- Public pages: app-style money and dates, "Amount paid" / "Invoice total" instead of
  "Amount due" once paid or voided, due date beside the amount, a refresh after payment,
  document-specific "link not available" pages, tokenised success states.
- Invoice and quote detail: copyable customer link; the customer name links to that
  customer.
- Customer emails say which business they are from, format money like the app, and escape
  names placed in HTML.
- Dashboard setup checklist is computed from real data and stays until complete (billing
  steps are skipped for Books- or Drive-only workspaces).
- Confirmations for role change, removing a member, revoking an invite and disabling a
  module. Developer wording removed from user-facing copy. Customer search has its own
  empty state.

**Mobile**

- Screens show the saved copy immediately and refresh in the background.
- Search is debounced; route reconcile is incremental; push registration only when
  something changed; no network auth call after each bootstrap.
- Pull-to-refresh on the four tab screens, tappable Home KPI tiles, 44pt filter pills,
  KPI trend styling, an assistant Stop button and confirmations.

**Platform**

- Security headers on every route (`apps/web/next.config.ts`).
- CI split into parallel jobs with a Turbo cache, keeping the `quality` check name.
  Dependabot configuration added.
- The quote acceptance email, when given, must be a valid address.

### Deferred from Wave 1, with the reason

- **Decimal tax rates.** `tax_rate` is an integer column and the create/update functions
  take an integer, so this needs a migration. Moved to Wave 6.
- **Invitation sign-up.** "Create account" from an invitation still goes through the
  workspace-builder sign-up and then onboarding; the invitee has to reopen the link.
  An invitation-aware sign-up belongs with the auth work in Wave 6.
- **Admin credit balance.** The admin area reads a separate `billing_credit_ledger`
  table with the same sum-in-code pattern. Left as is; whether two ledgers should exist
  is a question for Wave 2.
- **Invitation E2E.** The browser test still stops at "invitation is pending"; the link
  shape is covered by unit tests instead, because the test stack has email switched off.
- **Home KPI trends on mobile.** The tile supports a trend, but the overview payload has
  no previous-period values to feed it yet.
- **Assistant list limit.** The plan said 50; it is 100, so answers that add up a
  moderate list do not get worse before summary tools arrive in Wave 4.

## Wave 2: what changed

Wave 2 is "data correctness and speed foundations". Five of its nine roadmap items are
built (the cron item without its frequency review); the other four need a decision first
(see "Left from Wave 2"). Everything is in the working tree on top of Wave 1, uncommitted.

### Done

1. **Lists page past 100 rows.** Books, Drive (earnings and trips) and Customers used to
   stop at 100 rows with no way to see the rest. They now show 50 per page with Previous
   and Next, keeping the active filters in the page links, and an empty later page links
   back to the first (`utils/pagination.ts` `RECORD_PAGE_SIZE`, the three loaders, the
   three pages). Each loader reads one extra row to decide whether "Next" exists, so there
   is no count query. The Drive "New entry" page no longer loads the Drive list and period
   summary just to read the currency (`loadDriveEntryForm`).
2. **Searchable customer field.** Invoice, quote and Books forms listed only the 100 newest
   customers in a native select, so older customers could not be picked at all. A shared
   `components/customer-combobox.tsx` (on a new `components/ui/popover.tsx`) searches
   name, company and email, renders at most 50 matches, and keeps the id in a hidden input.
   Forms now load every active customer's name, company and email through
   `listCustomerOptions` (`server/foundation/customers/index.ts`), which reads past the
   1,000-row API cap in chunks, up to 5,000. Loading all of them, rather than searching
   the server, keeps hAI's "open a draft for Acme" working, because the form resolves the
   customer name against this list.
3. **Search does one customer lookup.** Invoices, quotes and Books each looked up matching
   customers before their own query, so one search ran that lookup three times (plus the
   customer group's own query). `findCustomerIdsMatching` now runs once per search, on web
   (`server/application/http/api/search/search.ts`) and mobile
   (`server/application/mobile/resources/overview.ts`), and the ids are passed to the
   list functions through a new `matchingCustomerIds` option. `/api/search` is limited to
   120 searches a minute per member (`SEARCH_RATE_LIMIT`), returning 429 past that.
4. **Faster signed-in pages.** Every page and action resolved the session, then checked
   the account was not deleted, then read the memberships, one after another. The account
   check and the membership read now run together (`getSessionIdentity` in
   `server/application/auth/session.ts`, used by `workspace-context.ts`); memberships are
   discarded if the account check fails. The membership query reads four workspace columns
   instead of all of them (it used to include payment settings).
5. **Scheduled jobs.**
   - Credit expiry read every grant that had ever expired, including ones reversed long
     ago, then ran one more query per grant. `list_due_credit_expiries` returns only grants
     that are due and not reversed yet, in batches of 200
     (`server/foundation/billing/credits.ts`).
   - The overdue-invoice and expired-quote jobs mark every due record in one update, then
     publish the event and audit row for each. That loop stopped at the first error, and
     the records after it never got their email, notification or audit row, because they
     were already marked and are not picked up again. `forEachSettled`
     (`server/infrastructure/for-each-settled.ts`) now runs five at a time and carries on
     past a failure, logging it.
   - Mobile idempotency records (`mobile_api_operations`) were never deleted. The
     per-minute mobile cron now deletes up to 1,000 completed records older than 90 days
     per run, through `prune_mobile_operations` and a new partial index. Records still
     processing are never deleted. A pruning failure is logged and does not fail the
     cron's delivery work.
6. **Saving twice cannot create two records.** Each create form now keeps one id per draft
   (`hooks/use-request-id.ts`) and sends it with every attempt. When a create fails and a
   record with that id already exists in the workspace, the earlier attempt went through
   and only its response was lost, so the action returns that record
   (`server/application/request-id-create.ts`). Covered: invoices, quotes, Books
   transactions, customers (form and the inline "Add customer" dialog), Drive earnings,
   trips (form and quick log) and vehicle expenses. A normal save runs no extra query.
   The "We couldn't confirm whether this … was saved" message now ends "Check invoices, or
   save again; this won't create a second invoice" (and the same for quotes and customers).
7. One flaky test fixed: the module-disable confirmation test clicked "Disable" while the
   first attempt could still be finishing; it now waits for the button.

### Left from Wave 2, with the reason

- **Durable notification outbox.** Needs a decision on where it is drained: a sixth cron
  entry (project notes keep five) or the existing per-minute mobile cron. The event-bus fix
  from Wave 1 made emails fire again; this is about not losing one if a server instance
  dies mid-send.
- **Mobile API: verify the token locally.** Faster, but a revoked session would keep
  working until its token expires (as on web today). That trade-off is yours to accept.
- **Caching and the React Compiler.** Adopting Next 16 Cache Components changes how every
  page renders; it needs a decision and a measured trial, not a quick change.
- **Dropping the nine redundant indexes.** Needs production index-usage statistics first.
- **Mobile cron frequency.** It still runs every minute; whether that is needed when the
  queues are empty depends on how quickly you want push notifications delivered.
- **Bulk Drive earnings entry** still has no per-draft id: its service creates several
  rows in one call and has no way to accept an id per row. It keeps its existing
  "check your earnings before trying again" guidance.

### Before deploying (Wave 2)

1. Apply `20261118100000_job_batching.sql` after the two Wave 1 migrations. The
   credit-expiry job fails without it; mobile pruning logs an error and carries on. Its two
   function types were added by hand: `list_due_credit_expiries` in
   `server/infrastructure/db/types.ts`, `prune_mobile_operations` in
   `server/infrastructure/db/mobile-types.ts`.
2. Mobile idempotency records are kept 90 days (`MOBILE_OPERATION_RETENTION_DAYS` in
   `server/application/mobile/jobs.ts`). A device that retries a queued change after that
   would create it again. Change the constant if your offline window is longer.
3. No new environment variables and no new cron entries.

## Wave 3: what changed

Wave 3 is "hAI you can trust": nothing hAI proposes changes a record until the person
approves that exact change, and the server, not the browser or the app, enforces it.
Paths are relative to `apps/web/src` unless they start with `apps/` or `supabase/`.

### Done

1. **Tests first.** `server/application/http/api/assistant/handler.test.ts` drives the real
   route and turn with a scripted model (`ai/test`), an in-memory conversation store and
   action ledger that keep the real rules (`testing/assistant-harness.ts`). It covers:
   a change pauses for approval and runs nothing; an approved change runs once and the
   same approval sent again is refused; two simultaneous approvals run it once; a decline
   runs nothing and later turns still tell the model it was declined; every waiting
   change needs a decision; a proposal edited after the fact is not run; a new message
   settles open proposals; an unknown tool is refused; an older app build cannot make
   changes; answer again, retry and the error cases.
2. **Free eval set.** `server/application/assistant/evals/assistant.eval.test.ts` runs five
   behaviour cases in CI by replaying a scripted model, including one where the model obeys
   an instruction planted in a tool result: the send is still held. The hard check in every
   case is that nothing ran without approval. `HAI_EVAL_LIVE=1` runs the same cases against
   the configured provider (costs money; the tools stay in-memory, so no data is touched).
3. **Whole messages.** `ai_messages` gains `parts` and `metadata`
   (`supabase/migrations/20261118110000_assistant_messages_and_actions.sql`). One row is one
   chat message: text, tool calls with results and approval state, and the approval
   preview. `content` keeps plain text for titles and older app builds; rows from before
   the migration show as text. One turn module (`server/application/assistant/turn.ts`)
   now serves the web route and the mobile routes, replacing the mobile-only wrapper
   (`server/application/mobile/assistant-tools.ts`, deleted) that guessed writes from tool
   names.
4. **Server-enforced approvals.** Write tools run through the SDK's `toolApproval`. Every
   proposed change is recorded in a new `ai_tool_actions` ledger before the person sees it:
   pending, then approved or denied, then running, then succeeded or failed. Each step is a
   single conditional update on the current status, so a repeated or simultaneous approval
   cannot run a change twice; a repeat returns the stored result. The browser and app send
   only `{ approvalId, approved }`. When the reply continues, the server checks the call
   still matches its stored proposal (tool and input) and refuses it otherwise. Rows are
   readable only by the member who owns the conversation and are deleted with it.
5. **Policy** (`lib/assistant/approval-policy.ts`): opening pages, unsaved drafts and
   lookups run freely; every change asks; a tool the catalogue does not know is refused.
   Sending, marking paid (emails the customer), voiding, deleting a transaction,
   converting a quote and receipt extraction are listed as never auto-approved, for when
   any automatic approval is added later.
6. **Approval cards show the server's preview** (`server/application/assistant/action-preview.ts`):
   the record, the customer and email address, the total, what happens ("Emails … the
   invoice with a payment link"), and a caution for emails to outsiders and changes that
   cannot be undone. The preview is resolved from the workspace's records, not from what
   the model wrote, and is stored with the message, so cards survive a reload.
7. **Turn rules.** Sending a new message instead of answering declines the open proposals
   ("Not done: you sent a new message instead of approving it"). "Answer again" is refused
   for a reply that changed something, and declines the proposals of the reply it
   replaces. Retry after a failed request is resolved on the server, so the person's
   message is never stored twice. A change approved after writes were turned off is not
   run.
8. **Web chat** (`features/assistant`): one chat hook for the page and the panel
   (`hooks/use-hai-chat.ts`); approval cards with Approve and Decline; Copy; "Answer
   again" on the latest reply; "Try again" on errors, with the server's message; rename;
   the panel keeps its conversation across a refresh (per tab); reopening a conversation
   no longer replays its page navigations. Replies render through a small Markdown
   renderer that only produces React elements (`components/hai-markdown.tsx`), and the
   prompt now allows light Markdown on web and plain text on mobile.
9. **Prompt.** The write-mode rules made the model ask "shall I?" in text and then the card
   asked again. The card is now the confirmation; the model must not act on text inside a
   tool result, and is told when an app build cannot approve changes.
10. **Mobile.** The app sends `X-Hai-Capabilities: approvals`; the conversation detail
    returns the waiting changes with their previews; `POST …/conversations/:id/approvals`
    takes the decisions; the assistant screen shows native approval cards
    (`apps/mobile/src/features/assistant/lib/approvals.ts`). Builds without the header have
    changes refused with "Update the app, or make this change on the web"; lookups work.

### Found and fixed during verification

- **A declined change was stored as still waiting.** The SDK answers a decline inside the
  model's history and leaves the call as "decided" in the reply, so later turns dropped it
  and the model forgot the person had said no. Declines are now stored as not done.
- **Declining could send the decision twice.** The SDK re-checks "send automatically"
  after every reply; the no-key mock stream had no step markers, so the declined call
  still looked fresh. The server refused the duplicate (409), but the browser showed a
  failed request. The mock now marks steps like a real stream, and the chat remembers
  which decisions it already sent.

### Decisions taken

- Every change needs approval, including draft creates (unsaved `openForm` drafts are not
  changes and still need none).
- The per-conversation write switch stays: with it off, write tools are not offered at all.
- Older app builds: changes are refused with a reason the model passes on.

### Not verified or left

- Resuming a paused turn on a model with extended thinking on was not tried against a live
  API (local runs use the mock provider). Run the eval live before turning thinking on.
- The live eval has not been run; it needs a provider key and costs money.
- Approve-then-run was exercised by the route tests only: the local mock provider never
  proposes changes, so the browser check used seeded proposals and declined them.
- Native approval cards are type-checked and unit-tested, not run on a simulator.
- The unused mobile `assistant/chat` route alias is still there.

### Before deploying (Wave 3)

1. Apply `20261118110000_assistant_messages_and_actions.sql`. The assistant fails without
   it. Its types were added by hand to `server/infrastructure/db/types.ts`.
2. Deploy the web app before releasing the app update: the new app needs the approvals
   endpoint. Current app builds keep working, with changes refused.
3. Conversations from before the deploy that ended with the model asking "shall I?" in
   text need the person to ask again; the card flow starts with the next request.
4. No new environment variables (`HAI_EVAL_LIVE` is for opt-in eval runs only) and no new
   cron entries.

### Found and fixed during review

Three read-only reviews (chat UI, server and data, caching and titles) were run before the
pull request.

- **Chat UI.** A question asked from elsewhere re-ran the navigation of the conversation on
  screen, and was sent again after a workspace switch. A conversation picked in History, or
  restored after a reload, could land on top of what the person did while it loaded. A
  receipt removed while uploading came back. A late reply could attach its conversation to
  a chat that had moved on. "Show more" could lose a row when the first page changed.
  Focus was dropped after the write-tools confirmation, "Show more" and removing an
  attachment. The reopened panel did not start on the newest message. The page pinned the
  title it loaded with. All fixed, each with a test.
- **Server and data.** A rating could never be saved on a long reply cut inside an emoji
  (stored text is now cut without splitting a pair, including first-message titles); `*`
  in a conversation search acted as a wildcard; a document number containing a quote threw
  a database error instead of "not found"; a period summary ending at midnight left out
  invoices paid that day; digest preferences were writable by a signed-in session and are
  now read-only like every other table; opening a conversation failed if its ratings could
  not be read. The feedback and conversation-list services and the assistant's server
  actions had no tests and now do.
- **Caching and titles.** Cache reads stopped at the first tool result in a
  conversation's history, because stored message parts come back with their JSON keys
  reordered: tool inputs and results are now sent in one key order in flight and on replay,
  and a declined change is sent the same way both times. A title the person set could be
  replaced when it happened to be the start of their first message; a title is now treated
  as automatic only when it matches exactly. The installed-modules list in the prompt is
  sorted, so row order cannot change the cached prefix. Work started after a stopped
  response closes is now kept alive. A receipt read that fails parsing records its usage.

  a lost response can duplicate an invoice/transaction.
- Mobile API auth does a network `auth.getUser(token)` plus a `users` lookup, a rate-limit
  call, membership and workspace reads on every request
  (`apps/web/src/server/application/mobile/http.ts:78-134`); the web proxy already uses
  local JWT verification (`getClaims`, `apps/web/src/proxy.ts`).
- `/api/cron/mobile` runs every minute (`apps/web/vercel.json`).
- Product gaps still open from the August review: business profile (ABN, logo, address),
  workspace document defaults (payment terms, tax, notes), scheduled invoice reminders,
  recurring invoices, bank import, cash forecast.
- `accepterEmail` on public quote acceptance is still not validated as an email
  (`apps/web/src/features/quotes/api/public/actions.ts:22`).

## Roadmap

Wave 1 is done and Wave 2 mostly done (see above). Waves 3 to 8 are scoped outlines to be
picked up one at a time; each should get its own short plan when started. Order within a
wave is by user impact.

### Wave 2: data correctness and speed foundations

Status: the first, second, fifth (except the cron-frequency review), sixth and seventh
bullets are done; the rest are listed under "Left from Wave 2".

- Paging for Books, Drive and Customers lists (reuse `ListPagination` and
  `utils/pagination.ts`) and a searchable customer picker shared by invoice/quote/books forms.
- Search: resolve matching customers once per request and pass the ids into the list
  functions; rate-limit `/api/search`.
- Durable notifications: outbox table drained by cron for email/PDF so nothing is lost if a
  deferred task dies (the mobile push outbox is the pattern to copy).
- Mobile API auth: verify the JWT locally as the web proxy does (trade-off to confirm: a
  revoked session stays valid until its token expires, as on web today).
- Crons: batch credit-expiry and overdue/expired work; prune `mobile_api_operations`; review
  whether the mobile cron needs to run every minute when queues are empty.
- `(app)` layout: run the profile and membership reads together; slim switcher columns.
- Web create idempotency keys (reuse the mobile operation ledger design).
- Caching decision: adopt Next 16 Cache Components for period summaries, or stay dynamic
  with SQL aggregates only. Trial the React Compiler behind a branch and measure.
- Drop the nine redundant left-prefix indexes after checking production usage stats.

### Wave 3: hAI you can trust

Built; see "Wave 3: what changed". The compare-and-set steps are conditional updates
rather than RPCs, since each step changes one row.

- Safety net first: route tests for `handler.ts` and an eval set that costs nothing by
  default (mock model from `ai/test`, recorded-response replay; live runs opt-in only).
- Store whole messages: `ai_messages` gains `parts jsonb`, `metadata jsonb`; one row is one
  UI message; a shared `server/application/assistant/turn.ts` serves web and mobile.
- Server-enforced approval using `toolApproval` on `streamText` (supported in the installed
  SDK) plus an `ai_tool_actions` ledger with compare-and-set RPCs. The client sends only
  `{ approvalId, approved }`; tool name and input always come from the server's stored copy.
  The ledger also makes execution idempotent on web and replaces the mobile name-regex
  wrapper.
- Policy: navigation and reads run freely; every write needs approval; `sendInvoice`,
  `markInvoicePaid` (it emails the customer), `voidInvoice`, `deleteTransaction`,
  `convertQuoteToInvoice` and `extractReceipt` can never be auto-approved; unknown tools are
  denied.
- Approval cards show a server-resolved preview (recipient, total, consequence such as
  "Emails ap@acme.com a payment link"); cards persist across reloads; retry, regenerate,
  copy, rename on web, panel thread survives refresh; a small no-dependency markdown
  renderer.
- Mobile: capability header so older builds have writes declined with a reason; approval
  endpoint and native cards in the next app release.
- Test before committing to the design: resuming a paused tool turn on a model with
  thinking on (unverified against the live API).

### Wave 4: hAI smarter answers and cost controls

Mostly built; see "Waves 4 and 5: what changed". Left: plan allowances and `assertAiBudget`,
`/admin/ai-usage`, `toModelOutput` compaction, and the chat model move.

- Usage ledger: `ai_usage_events` + `ai_usage_monthly` written by one RPC from `onEnd`;
  `assertAiBudget` before every call; allowance by plan with per-workspace override; usage
  bar in settings; `/admin/ai-usage` (cost by feature and model, cache-read ratio, top
  workspaces, failed actions). Kept separate from the money credit ledger.
- Prompt caching: stable prefix marked with `providerOptions.anthropic.cacheControl`;
  date and page context move into the user message so earlier turns stay byte-identical;
  confirm with `cacheReadTokens > 0`. Token-budgeted history trimming.
- New tools: `getInvoice`, `getQuote`, `getCustomer`, `getTransaction`, `getPeriodSummary`
  and `getGstSummary` (backed by the existing summary RPCs), `listReceiptQueue`; compact
  model payloads via `toModelOutput`.
- Move the default chat model to the current-generation Sonnet after a live eval run; light
  tier for titles and phrasing. Note: in the installed provider version, structured output
  on Haiku 5.5 / Opus 5.5 falls back to a forced tool call those models reject, so receipts
  stay on the Sonnet tier until the provider package is upgraded.
- Entry points: "Ask hAI" in the command palette, on the dashboard and on record pages with
  the record passed as context.

### Wave 5: hAI proactive insights

Built without any model call; see "Waves 4 and 5: what changed" for what was dropped.

- `collectInsightFacts()` builds deterministic facts from SQL (overdue, due in 7 days,
  quotes expiring, receipts to review, unusual spend, GST due); the dashboard "Needs
  attention" list reuses it. Numbers never come from the model.
- Dashboard briefing card read from an `ai_briefings` cache (one per workspace per local
  day); rendering never calls a model.
- Digest: hourly cron claims opted-in workspaces whose local send time has passed; in-app
  notification plus email with unsubscribe; the light model writes at most a two-sentence
  headline, rejected if it contains a number not in the facts; facts-only fallback when the
  provider is off, over budget or errors; nothing sent when there is nothing to report.
- Settings: workspace opt-in (default off) and per-user daily/weekly/off.
